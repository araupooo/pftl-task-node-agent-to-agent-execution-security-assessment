# Credential lifecycle policy

[ANALYSIS] A policy specification for agent credentials. It applies
to the reference design in `docs/auth-design.md`; whether the live
platform follows any of it is UNVERIFIED (C-32, C-33).

## 1. Issuance

- An agent keypair is generated by the agent itself, in its own
  environment. The private key never leaves that environment.
- The agent registers its public key with the platform. Identity is
  `agent-` + first 16 hex of SHA-256(public key).
- Capability tokens are issued by the platform issuer, never by the
  agent, and are signed with the issuer key. A token binds exactly
  one agent, one task, and an explicit capability list.
- A token is issued only after the agent has accepted the task it
  names. No standing tokens.

## 2. Validity

| Credential | Lifetime | Rationale |
| --- | --- | --- |
| Capability token | 1 hour | Bounds the exposure window if a token leaks |
| Signed task action | 900 s (15 min) | Bounds replay value; nonces cover the rest |
| Agent keypair | 90 days, then rotated | Limits the value of a silently exfiltrated key |
| Issuer key | 1 year, then rotated | Platform-wide impact if lost; rotation is a planned event |

## 3. Rotation

- **Agent keys:** rotate every 90 days, or immediately on any
  suspicion of compromise. Rotation = generate a new keypair,
  register the new public key, revoke the old one. In-flight tasks
  keep their old tokens until expiry (at most 1 hour), then receive
  new tokens under the new key.
- **Issuer keys:** rotate yearly with a 30-day overlap: both the old
  and new public keys are trusted during the overlap, tokens are
  issued under the new key, and the old key is retired at the end
  of the window.
- **Emergency rotation:** any confirmed compromise triggers
  immediate rotation regardless of schedule
  (docs/incident-response.md, Phase 2).

## 4. Expiry

- Expired tokens are rejected, never renewed in place. An agent
  that needs more time requests a new token for the same task.
- Expired actions are rejected (drill D-11). An agent whose action
  expired re-signs with a fresh timestamp and nonce.

## 5. Revocation

- Revocation is by agent id, effective immediately, and checked on
  every verification (drill D-10).
- The revocation list must propagate to every verifier within a
  stated maximum delay (recommendation: under 60 s).
- Every revocation is logged with the reason, the operator who
  ordered it, and the timestamp.
- Revocation is not reversible by the agent; only the platform
  operator can remove an entry, and only after the underlying
  compromise is resolved.

## 6. Storage and handling

- Agent private keys are stored in the agent's own secret store,
  never in task evidence, logs, or shared memory.
- No credential — key, token, or nonce — is ever written into a
  public evidence pack, a task record, or a support ticket.
- Logs record agent ids and decision reasons, never signatures or
  key material.

## 7. Audit

- Quarterly: list all active agent keys older than 90 days and
  rotate them; list all tokens issued in the quarter and confirm
  each maps to a real task.
- After every incident: review the audit log against
  docs/incident-response.md Phase 3.
